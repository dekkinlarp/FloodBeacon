# FloodLens SMS intake (`twillio`)

Python service for Twilio SMS reports, Gemini extraction, location follow-up conversations,
and an authenticated API for an operational map. The directory spelling `twillio` is intentional;
the provider and SDK are **Twilio**.

## Setup

Requires Python 3.11+. Run from this directory:

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

`requirements.lock.txt` records the exact dependency versions used for the passing tests;
use `pip install -r requirements.lock.txt` to reproduce that environment.

Edit `.env` with Gemini credentials/model, Twilio account SID/auth token/number, your exact
external webhook URL and a random operator API key. Generate a key with:

```sh
python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Start the API and then the worker in separate terminals with the same environment:

```sh
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

```sh
python -m app.worker
```

Use **one worker process** for this SQLite MVP. Both processes must share `DATABASE_PATH` on
persistent storage. Configure your Twilio number's incoming Messaging webhook as an HTTPS POST
to `https://your-host.tech/webhooks/twilio/inbound`. A tunnel can expose localhost for development.
`TWILIO_WEBHOOK_URL` must exactly match the public URL, including any query string. Signature
validation uses this configured URL so reverse proxies do not substitute a localhost URL.

`SMS_DRY_RUN=true` is the default: questions are saved as previews in `/outbox`, and **no SMS
is sent**, including receipt acknowledgements. Set it to `false` in both processes and restart
for a live conversation. Old previews are not automatically sent. Twilio and Gemini have their
own billing; free satellite data does not make messaging/model inference free. No keys are included.

## Conversation

Synthetic example, not a real rescue request:

1. Person: `Four of us need help upstairs on Example Road in Abbotsford. Water is rising.`
2. Service acknowledges receipt in live mode, explicitly stating no rescue was dispatched.
3. Worker asks for the house/building number.
4. Person: `123A`
5. Worker asks for the postal/ZIP code, explicitly distinguishing it from telephone area code.
6. Person: `UNKNOWN`
7. The model retains house number `123A`, a null postal code and the explicit unknown status.

One question is asked at a time, in this order: house number, street, city/locality, postal/ZIP
code, then landmark if needed. Questions are fixed templates, not model-generated instructions.
Each field is asked at most once per conversation. Unknown or unavailable address details do
not block the report. Gemini uses the recorded preceding question to interpret short replies.
House numbers are strings. Telephone area code is a separate optional field, never a substitute
for postal code or a geographic position. Coordinates are never generated by Gemini.

`NEW` starts a separate report; sessions expire after `SESSION_HOURS` (default 6). A sender's
phone number never merges separate conversations. Within a conversation, a versioned case
snapshot contains separate situations for separate households. Counts are not summed. Multiple
locations remain unlocated pending operator handling. Automatic geocoding, incident matching
and case splitting are integration boundaries, not implemented in this MVP.

STOP-family commands suppress queued follow-ups for the sender/recipient; START/UNSTOP allow
future questions. Also configure Twilio's opt-out handling. An SMS already in flight cannot be
recalled. Suppressed or failed questions are visible to operators but not automatically repeated.

## Storage and reliability

- `messages`: original SMS, unique Twilio SID, timestamps, processing state, attempts.
- `conversations`: private sender/recipient references, asked fields, opt-out state.
- `extractions`: immutable Gemini output versions, evidence, model and prompt versions.
- `incidents`: current assessment case, verification, response, human priority and reviewed location.
- `audit`: before/after records of extraction and operator edits.
- `outbox`: follow-up questions and submission results.

The webhook stores work before returning and deduplicates by SID. A worker processes messages
in conversation order. A 180-second job lease supports recovery; failures retry up to three
times with a 30-second delay. Failed and pending original reports remain visible in `/reports`.
Evidence quotes must occur in cited messages. This detects fabricated citations, not semantic
extraction errors: human review is still required. Phone envelope fields are not sent to Gemini.

New extractions never dispatch, close an incident, or change human-assigned priority. A claim
of safety is only `reported_resolution`. Address changes clear previously reviewed coordinates.

Outbound SMS is not exactly-once: a timeout may occur after provider acceptance. Ambiguous
sends become `uncertain`; crashes during sending leave `sending`. Neither is automatically
resent. Inspect Twilio logs to reconcile. `sent` means accepted by Twilio, not delivered to a
phone. Delivery-status callbacks are not implemented.

## API

`/health` is public; the webhook requires a valid Twilio signature. All following routes require
`Authorization: Bearer <OPERATOR_API_KEY>`. Keep that key on the map application's backend,
not in a public browser bundle. Interactive API schemas are at `/docs`.

| Endpoint | Purpose |
|---|---|
| `GET /reports/gemini` | JSON list of saved Gemini reports per incoming message |
| `GET /reports` | Original reports, including pending, failed and unrelated messages |
| `GET /incidents` | Current assessment cases and extracted fields |
| `GET /reports/unlocated` | Cases needing location resolution |
| `GET /incidents/{id}` | Case, original messages, extraction versions and audit history |
| `PATCH /incidents/{id}` | Human verification, priority, response and coordinates |
| `GET /incidents.geojson` | Located cases, without original messages or contact details |
| `GET /outbox` | Proposed questions and preview/submission/failure states |

Example operator PATCH using the current version returned by GET:

```json
{
  "expected_version": 1,
  "reason": "Checked the address against our address dataset",
  "latitude": 49.0,
  "longitude": -122.0,
  "location_precision": "approximate",
  "location_source": "operator-reviewed address match",
  "verification_status": "corroborated"
}
```

These coordinates are illustrative. Stale versions return HTTP 409. Coordinates require both
axes, precision and source together. `clear_location: true` removes a point. Multiple-location
cases cannot receive one point. GeoJSON uses longitude-first coordinates and excludes unlocated
cases; keep `/reports/unlocated` visible beside the map. Original reports and precise locations
belong in an authenticated operational view. No public map publication is included.

`report.situations[].address` includes `house_number`, `street`, `unit`, `city`, `region`,
`country`, `postal_code`, `telephone_area_code`, `landmark`, `location_detail`, and
`unavailable_fields`. Unknown values are null. API timestamps are Unix UTC seconds.

## Tests

```sh
python -m pytest -q
```

Tests use isolated databases and fake providers; they send no texts and need no credentials.
Live end-to-end testing requires your accounts and a controlled test number. Use labeled synthetic
reports when replaying the historical Sumas Prairie flood.

This hackathon prototype is not an emergency dispatch service. For real deployment, add
organizational authentication/roles, per-user audit identity (currently shared `operator`),
encrypted storage/backups, retention controls, monitoring, provider delivery reconciliation,
operator-managed matching/splitting, and an operational review. Protect original SMS and the
SQLite database as sensitive data.

## Get Gemini reports as a JSON list

The existing FastAPI server exposes `GET /reports/gemini`. No separate server or Gemini call
is needed for a GET request. The worker must run to generate reports from received messages.

```sh
curl --get 'http://127.0.0.1:8000/reports/gemini' \
  --header "Authorization: Bearer $OPERATOR_API_KEY" \
  --data-urlencode 'limit=100'
```

Export `OPERATOR_API_KEY` into your terminal first; the server loading `.env` does not export
it into your shell. In Postman, use GET and Bearer Token authentication with that same key.
For remote access replace localhost with your public API host, keeping `/reports/gemini`.

The response is a JSON array, newest message first. An illustrative pending entry:

```json
[
  {
    "message_sid": "SM_example",
    "conversation_id": "example-conversation-id",
    "received_at": 1791050400.0,
    "processing_status": "pending",
    "error": null,
    "extraction_id": null,
    "generated_at": null,
    "model": null,
    "prompt_version": null,
    "report": null
  }
]
```

Once processed, `processing_status` becomes `extracted`, extraction metadata is populated,
and `report` is a nested JSON object (not an escaped JSON string). It contains `report_type`,
`situations`, `missing_information`, and `conflicts`. Each situation includes summary, people
count, hazards, assistance needs, evidence, and the structured address fields described above.
Pending/processing/failed messages remain visible with `report: null`; `error` is the stored
failure class when applicable. A report being extracted does not mean it has been verified.

Query parameters:

| Parameter | Default | Behavior |
|---|---|---|
| `message_sid` | absent | Return the matching message in a list, or `[]` |
| `conversation_id` | absent | Limit results to one SMS conversation |
| `help_only` | `true` | Include rescue requests, updates, and not-yet-classified messages; exclude extracted `other` reports |
| `limit` | `100` | Page size, 1–500 |
| `offset` | `0` | Number of matching messages to skip |

Control messages such as STOP/NEW are always excluded. Use `help_only=false` to include
unrelated completed extractions for debugging. Pagination is newest-first offset pagination;
new arrivals can shift page boundaries, so consumers should deduplicate by `message_sid`.

Each item is the saved conversation snapshot as of that message. Follow-up replies therefore
produce separate versions for the same conversation. Do not sum their people counts or plot
each version as a separate rescue. Use `/incidents` for the current operational case and
`/incidents.geojson` for reviewed coordinates. This endpoint omits phone-envelope fields and
raw message bodies, but reports can still contain sensitive address details and evidence quotes;
it requires operator authentication and sets `Cache-Control: no-store`.


## Verified model configuration

The configured default is `gemini-3.5-flash`. During troubleshooting on October 3, 2026,
`gemini-3.8-flash` returned repeated 503s for extraction requests through both SDK and direct
HTTP calls. The same schema and evidence validation succeeded with `gemini-3.5-flash`.
A synthetic two-message conversation also passed through the worker, address follow-up,
and `/reports/gemini` endpoint using an isolated database and dry-run SMS. This isolates the
observed failure to the model route; it does not establish Google's internal cause or guarantee
future availability. Restart the worker after changing `GEMINI_MODEL` in `.env`. Messages already
marked `failed` do not automatically retry; send a new test message to verify the updated worker.

## Synthetic Vancouver dashboard data

From `twillio/`, using the project virtual environment:

```bash
python -m app.seed_vancouver
```

This populates the SQLite database configured by `DATABASE_PATH` in `.env` with
12 fictional Vancouver cases: 10 approximate neighbourhood map points and two
unlocated reports. The cases cover evacuation, medical and mobility assistance,
supplies, and a simulated resolved report. All remain unverified; operational
priorities and response statuses are exercise fixtures. House numbers and postal
codes remain unknown rather than suggesting real households are in danger.

Every summary and source message is labeled `[SYNTHETIC VANCOUVER DEMO]`.
Extraction metadata uses `synthetic-fixture`, not a Gemini model. Messages are
already extracted, demo conversations are opted out, and no outbound SMS jobs
or Gemini requests are created. Original message evidence and audit records are
included for the detail panel. Stable `demo-vancouver-*` IDs make reruns skip
existing fixtures, preserving dispatcher edits and other reports.

Before seeding an existing database, the command creates a consistent SQLite
backup in its adjacent `backups/` directory. To seed a separate database instead:

```bash
python -m app.seed_vancouver --database data/vancouver-demo.sqlite3
```

The live dashboard receives these through the normal authenticated `/incidents`
feed. Connect it to the same backend/database and refresh the page to fit the map
to the loaded locations. Do not use `?demo=1`, which uses the original static demo.

## Gemini latency and timeouts

`GEMINI_TIMEOUT_SECONDS` defaults to 90 (allowed range 5–300). The SDK makes
one attempt per worker attempt; the persistent queue owns retries. Transient
failures such as HTTP 429/503/504 retry up to three total attempts, with delays
of 10–15 then 20–25 seconds. HTTP 400/401/403/404/422 fail immediately for review.
The message lease exceeds the configured request timeout by 60 seconds.
Logs record model, timeout, history size, elapsed time and next retry delay,
without logging SMS bodies or credentials. The worker remains sequential;
its periodic status line waits for the current request to finish.

Restart `python -m app.worker` after code or configuration changes. A 504 means
the provider did not complete within its deadline; a larger client deadline
may help but does not fix provider congestion. Failed records are retained and
are not automatically replayed on restart. Diagnose with synthetic input rather
than replaying a real message, which could cause a new SMS follow-up.
